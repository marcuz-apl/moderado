# M7.5 MCP CLI Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Give Moderado a safe `/mcp` popup that manages local stdio MCP servers and refreshes their tools in the active CLI session.

**Architecture:** The contracts package adds the persisted enabled state. The CLI owns MCP configuration CRUD, popup control flow, and rebuilding the registry; tools remains the bounded stdio transport and adapter owner. Core remains unchanged and receives the refreshed registry through its existing dependency injection boundary.

**Tech Stack:** TypeScript, Node.js standard library, Zod, Vitest, existing layered terminal popup utilities.

**Spec:** `docs/superpowers/specs/M7.5-mcp-cli-management-design.md`

## Global Constraints

- Support only explicit local stdio MCP configuration: fixed executable and fixed arguments.
- Do not add a dependency, a remote MCP transport, OAuth, a marketplace, prompts/resources, or automatic installation.
- Start every server with `shell: false` and sanitized environment; retain current output/time bounds.
- Every MCP invocation must require approval, including TUI auto-approve; non-interactive use must fail closed.
- Keep `packages/core` unaware of MCP transport and CLI management.
- Run all automated tests offline with a fake local stdio server.

## Review Focus

- A prior config without `enabled` must continue to load as enabled; Task 1 has the regression test.
- A disabled server must expose no tools after a reload; Task 2 has the registry test.
- A broken server must appear as a status error without disabling built-in tools or other MCP servers; Task 2 has the isolation test.
- An invalid add must never write configuration; Task 3 tests failed probe and invalid name paths.
- General TUI auto-approval must not bypass MCP approval; Task 4 tests the special approval path.

```ts
export const McpServerConfigSchema = z.object({
  executable: z.string().min(1),
  args: z.array(z.string()).max(32).default([]),
  enabled: z.boolean().default(true),
});

export function setMcpServerEnabled(name: string, enabled: boolean, customHome?: string): void {
  const config = loadConfig(customHome);
  const server = config.mcpServers?.[name];
  if (!server) throw new Error(`MCP server '${name}' is not configured.`);
  saveConfig({ mcpServers: { ...config.mcpServers, [name]: { ...server, enabled } } }, customHome);
}
```

- [x] **Step 3: Implement discovery status and a narrow reload helper**

```ts
export interface McpServerStatus {
  name: string;
  enabled: boolean;
  tools: McpTool[];
  error?: string;
}

export async function discoverMcpServers(servers: Record<string, McpServerConfig> = {}): Promise<McpServerStatus[]> {
  return Promise.all(Object.entries(servers).map(async ([name, server]) => {
    if (!server.enabled) return { name, enabled: false, tools: [] };
    try { return { name, enabled: true, tools: await listMcpTools(server) }; }
    catch (error) { return { name, enabled: true, tools: [], error: error instanceof Error ? error.message : 'MCP discovery failed.' }; }
  }));
}
```

In chat composition, change the registry binding from `const tools` to `let
tools`. Implement a local `reloadMcpTools()` that reloads config, calls
`createMcpTools`, and assigns `tools = createDefaultToolRegistry(mcpTools)`.
It must retain all built-in tools and not alter provider/session state.
