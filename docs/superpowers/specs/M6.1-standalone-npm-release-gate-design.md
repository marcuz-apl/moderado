# M6.1 Standalone npm Installation and Release Gate Design

**Date:** 2026-09-19  
**Milestone:** M6.1 — Standalone npm installation and release gate

## Goal

Make the published `moderado` npm package work after `npm install -g moderado`
without requiring a source checkout or unpublished `@moderado/*` packages.
Add a release workflow that verifies that package before a maintainer can
publish it.

## Packaging

The repository remains an npm workspace for development. The CLI package is
still the only public package. Its production build creates a small vendored
runtime under `apps/cli/dist/` containing the compiled internal workspace
modules. During that build, a repository-owned Node script rewrites only the
known internal module specifiers (`@moderado/contracts`, `@moderado/core`,
`@moderado/providers`, and `@moderado/tools`) to relative vendored paths.

This keeps TypeScript source imports and development workspace boundaries
unchanged. It avoids publishing private implementation packages, adding a
bundler dependency, or relying on `node_modules` inside the npm tarball. Third
party dependencies, currently `zod`, remain declared normal npm dependencies.

The build fails if a known workspace package has no compiled output or an
unrecognized `@moderado/*` import remains in the packaged runtime.

## Package verification

An offline Node verification script runs after compilation:

1. Run `npm pack --json` for `apps/cli`.
2. Inspect the tarball file list and reject source, tests, local configuration,
   sessions, logs, credentials, and any `node_modules` content.
3. Install the tarball into a fresh temporary npm prefix using only the
   package's declared dependencies.
4. Run the installed `moderado --help` and require successful exit with the
   expected command text.
5. Delete the temporary directory even when verification fails.

The command is deterministic and does not make provider calls, access user
configuration, or require an API key. Package installation may fetch declared
npm dependencies in CI; local offline unit tests cover tarball validation and
the verification command is a release check rather than part of `npm test`.

## Release workflow

`.github/workflows/release.yml` runs only when a maintainer pushes a version
tag matching the root `VERSION` SemVer portion, or explicitly starts it with
`workflow_dispatch`. It checks out the exact revision, uses Node 20, runs the
offline test suite and TypeScript build, runs standalone-package verification,
and uploads the `.tgz` as a GitHub Actions artifact.

The initial workflow does **not** invoke `npm publish`. A later, separately
reviewed opt-in step may use npm trusted publishing with GitHub Actions OIDC.
That step must be environment-protected and must never accept a stored npm
access token. This staged approach makes the release artifact reviewable before
the public registry is changed.

## Documentation

The README will replace source-checkout-first installation with the supported
global npm command and retain source checkout instructions for contributors.
The maintainer guide will document tag matching, artifact review, and the
future trusted-publishing prerequisite.

## Acceptance criteria

- A packed tarball installs into an empty prefix and `moderado --help` works.
- The public tarball contains only the CLI runtime, vendored internal runtime,
  license, and README; it contains no user data or source/test files.
- A release workflow verifies the package and uploads an artifact, but cannot
  publish to npm.
- The normal offline `npm test` suite stays provider-free and deterministic.

## Exclusions

M6.1 does not publish to npm, generate native binaries, create a curl
installer, sign artifacts, auto-update the CLI, or submit third-party
package-manager manifests.
