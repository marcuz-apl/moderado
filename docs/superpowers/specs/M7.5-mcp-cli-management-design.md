# M7.5 MCP CLI Management Design

**Milestone:** M7.5 — MCP CLI management and release gate

## Goal

Complete Moderado's existing local MCP foundation with safe, discoverable CLI
management so a user can configure, inspect, enable, disable, and remove a
trusted local MCP server without editing JSON by hand or restarting Moderado.

## Scope

M7.5 supports local stdio MCP servers only. A server has a user-chosen name,
an executable, a fixed argument list, and an enabled state. Existing server
records without an `enabled` field remain enabled for backward compatibility.

The interactive `/mcp` command opens a popup layer above the current welcome
or chat screen. Its menu provides:

- **List/status:** configured server name, enabled state, executable, and a
  fresh tool-discovery result or a clear connection error.
- **Add:** prompt for a validated name, executable, and a space-delimited,
  fixed argument list; probe `tools/list` before saving.
- **Enable/disable:** change only the enabled state. Disabled servers remain
  visible and preserved in configuration but contribute no agent tools.
- **Remove:** show a confirmation popup before deleting a server record.

Configuration changes take effect in the current chat session. The CLI rebuilds
only the MCP portion of the tool registry; it neither reconnects the provider
nor discards the active session.

## Trust and safety boundary

The current M4.3 boundary remains unchanged:

- Moderado never installs, downloads, or accepts an MCP server configuration
  from a model response.
- No remote HTTP/SSE transports, OAuth, server marketplace, prompts, or
  resources are introduced.
- Server commands run with `shell: false`, a sanitized environment, bounded
  frames, a timeout, and bounded text output.
- Every discovered MCP tool is namespaced `mcp.<server>.<tool>`.
- Every MCP invocation requires an interactive approval, even if the TUI's
  general auto-approve switch is enabled. Non-interactive use fails closed.
- MCP output is untrusted text and cannot alter workspace, provider, approval,
  or configuration policy.

A malformed, unavailable, or failing server is represented as an error in the
status popup. It must not prevent normal built-in tools, provider chat, or
other configured MCP servers from functioning.

## Architecture

`packages/contracts` extends `McpServerConfigSchema` with `enabled`, defaulting
to `true`. `packages/tools` remains the only owner of the stdio JSON-RPC
transport and MCP adapter. Its server-discovery helper skips disabled entries
and reports each server independently rather than failing the entire registry.

`apps/cli/src/config.ts` owns validated CRUD helpers for the `mcpServers`
configuration record. It continues to reject invalid names and malformed
records when loading persisted configuration.

`apps/cli/src/commands/chat.ts` owns the current-session MCP registry reload.
It passes an `onMcp` callback to the existing TUI input loop. `welcome.ts`
recognizes `/mcp`, displays it in completion suggestions, and routes it through
the same layered-popup mechanism used for `/session` and `/workflow`.

The core agent loop remains unaware of MCP management and transports. It sees
only ordinary registered tool definitions and continues applying its normal
declaration, validation, and approval flow.

## Error handling

An add operation does not write configuration until name validation and the
local `tools/list` probe both succeed. If the executable cannot start, times
out, or returns malformed MCP data, the popup shows the error and leaves the
existing configuration untouched.

A reload after enable/disable/remove preserves built-in tools. If a newly
configured server becomes unavailable later, only that server's tools are
omitted and the status view communicates the failure.

## Testing

Offline tests use a fake local stdio MCP server. They cover enabled defaults,
configuration CRUD and validation, status discovery, disabled-server omission,
per-server failure isolation, runtime registry reload, namespace preservation,
and the stronger MCP approval rule. TUI tests cover `/mcp` completion and
routing without requiring a live provider or terminal.

## Documentation and release relevance

README and SECURITY documentation describe the `/mcp` workflow, local-only
scope, and approval rule. The roadmap identifies M7.5 as the MCP release gate.
M7.5 is complete only when focused tests, the full offline suite, TypeScript
build, and a manual popup flow all pass.

## Exclusions

Remote MCP, OAuth, marketplace discovery, automatic installation, persistent
server processes, MCP prompts/resources, and desktop hosting stay out of
M7.5. They are optional future work and do not block the CLI public preview.
