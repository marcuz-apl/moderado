# M6.2 Standalone Binaries and Checksums Design

**Date:** 2026-09-19  
**Milestone:** M6.2 — Standalone binaries and checksums

## Goal

Produce portable Moderado executables for Windows, macOS, and Linux, with
checksums and release metadata that identify the exact source version. The
artifacts must run without Node.js being preinstalled.

## Binary builder

M6.2 adds `@yao-pkg/pkg` as a development-only dependency. It packages the
already verified CLI runtime and its ESM dependency graph into one executable.
The existing TypeScript workspace source and the standalone npm tarball remain
unchanged.

The binary build targets are:

- `node20-win-x64` as `moderado-win-x64.exe`;
- `node20-macos-arm64` as `moderado-macos-arm64`;
- `node20-linux-x64` as `moderado-linux-x64`.

The initial release deliberately omits Windows ARM64, macOS x64, Linux ARM64,
and Alpine. Each target has a build and smoke-test command before it is added.

## Artifact layout and integrity

The build writes artifacts under `artifacts/<VERSION>/`. For each executable,
it writes a `<name>.sha256` file containing the SHA-256 digest and filename.
It also writes `manifest.json` with the connected VERSION, Git revision when
available, artifact filenames, platform/architecture, byte size, checksum, and
an explicit `signed: false` field.

The manifest and checksums are generated from the final executable bytes. A
verification script fails on a missing artifact, malformed checksum, duplicate
platform target, or manifest/version mismatch. Artifacts and manifests contain
no provider credentials, sessions, local configuration, or diagnostic logs.

## Release workflow

The existing release workflow retains its npm package verification job. A
second matrix job builds one binary per operating system, smoke-tests it using
`--help`, and uploads its artifact directory. A final metadata job combines
the validated binaries into the release artifact bundle. The workflow keeps
read-only repository permissions and cannot publish packages or releases.

The workflow runs on explicit dispatch and matching version tags. It never
requires signing certificates. macOS quarantine/notarization and Windows
SmartScreen reputation are outside M6.2; documentation must say binaries are
unsigned.

## Verification

Offline unit tests cover target naming, manifest shape, checksum generation,
and rejection of tampered artifact bytes. The binary smoke tests are release
checks, because packaging relies on the development dependency and target
runtimes. They never call model providers or require API keys.

## Acceptance criteria

- Each supported target produces one executable whose `--help` command exits
  successfully on its matching runner.
- Each artifact has a SHA-256 checksum and a matching manifest entry under the
  unchanged connected identifier `v0.2.21+260919v`.
- The release workflow uploads verified binary artifacts but does not publish
  them or create a GitHub release.
- Documentation tells users which platforms are supported and that artifacts
  are unsigned.

## Exclusions

M6.2 does not sign, notarize, publish, auto-update, install, or submit any
artifact to a third-party package manager. M6.3 owns package-manager channels.
